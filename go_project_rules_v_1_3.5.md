# GO PROJECT RULES — Metrica Pro

## Версия 1.3&#x20;

Документ задаёт единый жёсткий стандарт разработки, тестирования, деплоя и эксплуатации **всех** Go‑проектов экосистемы Metrica Pro, без разделения по уровням зрелости.

Стандарт обязателен для:

- API‑серверов и микросервисов
- фоновых воркеров и обработчиков очередей
- локальных приложений (desktop/web, single binary)
- CLI‑утилит
- интеграций (внешние API, webhooks)
- IoT‑агентов и сервисов телеметрии

Любое отступление от стандарта требует отдельного письменного решения архитектора/техдиректора с фиксацией в репозитории.

# 1. ОБЩИЕ ПОЛОЖЕНИЯ

## 1.1. Минимальные версии и платформа
Перед развёртыванием идёшь в репо и проверяешь Latest версии бибилотек использованием. 
- Go: **>= 1.25**, патч‑версия всегда последняя доступная.
  - CI должен использовать одну конфигурируемую переменную `GO_VERSION`.
- PostgreSQL: **>= 18.x** (актуальная минорная версия).
  - Допускается временный fallback на **PostgreSQL 17.x** только при объективных ограничениях DBaaS.
  - Использование EOL‑версий PostgreSQL запрещено.
- SQLite: **>= 3.50.2**, только CGo‑free драйвер (`modernc.org/sqlite`).
  - Разрешено только для локальных/embedded‑сценариев и интеграционных тестов.
- Redis: **>= 7**, production‑подключение только по `rediss://` с проверкой TLS.
- Целевые платформы для бинарей:
  - Linux: `amd64`, `arm64` (основные таргеты для серверов и IoT‑шлюзов).
  - Windows: только для локальных desktop/edge‑бинарей.

Любой проект на Go внутри компании обязан поддерживать сборку минимум под Linux `amd64`.

## 1.2. Архитектурные принципы

1. **Чистое разделение слоёв**:
   - HTTP/transport (Echo handlers, gRPC handlers, consumers)
   - services (бизнес‑логика, транзакции, orchestration)
   - repositories (SQL/хранилища)
   - domain (сущности и бизнес‑типы)
   - components (повторно используемая бизнес‑логика, алгоритмы)
2. **Stateless API**:
   - Любой HTTP‑/gRPC‑сервис stateless по отношению к бизнес‑состоянию.
   - Состояние хранится в БД, кэше или внешних хранилищах.
3. **Строгая типизация**:
   - Go + OpenAPI/JSON Schema определяют жёсткие контракты.
4. **Высокая отказоустойчивость**:
   - retry, backoff, circuit breaker, panic‑recovery, timeouts.
5. **Observability по умолчанию**:
   - OpenTelemetry (трейсы, метрики), структурные логи, correlation IDs.
6. **Безопасность по умолчанию**:
   - секреты только из ENV/Secrets/Vault,
   - шифрование чувствительных данных в БД,
   - HTTPS/TLS для внешнего трафика,
   - минимизация surface area.
7. **Совместимость с TypeScript‑бэкендом**:
   - схемы PostgreSQL согласованы со схемами ERP/CRM на TS.
8. **Фреймворк Echo как стандарт HTTP‑роутера**
   - Echo используется как дефолтный HTTP‑router/фреймворк во всех проектах.
   - Весь бизнес вынесен в сервисы и компоненты, Echo не протекает в домен.

## 1.3. Сборка, артефакты и способ запуска

1. Стандартный артефакт сборки любого Go‑сервиса — **один бинарь** и **контейнерный образ**, построенный на его основе.
2. Наличие Dockerfile в репозитории **обязательно**, даже если в production сервис запускается не в Docker:
   - Dockerfile фиксирует эталонный способ сборки бинаря (Go‑версия, флаги, `CGO_ENABLED=0`, окружение);
   - используется в CI для job `docker-build` и security‑сканирования образа;
   - обеспечивает воспроизводимость сборки во времени.
3. Конкретный способ запуска в окружениях (dev/stage/prod) выбирается проектом и может отличаться:
   - прямой запуск бинаря (локально, через cron, через любой process supervisor);
   - unit‑файлы systemd/аналогичные механизмы;
   - запуск контейнера в Kubernetes/другом оркестраторе.
4. Требование стандарта:
   - бинарь, который запускается в production, **должен быть собран теми же параметрами**, которые заданы в Dockerfile (либо непосредственно через Docker, либо через reuse шагов CI);
   - использование Docker/Kubernetes **в рантайме не является обязательным**, обязательным является наличие описанного и проверяемого процесса сборки и образа, пригодного для деплоя при необходимости.

# 2. СТАНДАРТНЫЙ СТЕК

## 2.1. Библиотеки

В каждом проекте по умолчанию используется следующий стек (обновлённые версии фиксируются в version‑matrix репозитория):

- `github.com/golang-migrate/migrate/v4` — миграции
- `github.com/google/uuid` — UUID (fallback для SQLite/утилит)

- `github.com/redis/go-redis/v9` — Redis client (TLS)
- `github.com/rs/zerolog` — structured logging
- `github.com/sony/gobreaker` — circuit breaker
- `github.com/go-playground/validator/v10` — валидация DTO
- `github.com/caarlos0/env/v10` — конфигурация через ENV
- `golang.org/x/sync/errgroup` — управляемая конкуррентность
- `github.com/deepmap/oapi-codegen/v2` (или актуальный) — OpenAPI codegen

Использование альтернативных библиотек допускается только после архитектурного review и фиксируется в ARCHITECTURE.md.

## 2.2. Проверка зависимостей

Для всех внешних зависимостей обязательно:

1. Проверка через deps.dev и аналогичные инструменты:

   - нет High/Critical CVE;
   - активность репозитория в течение последних 12 месяцев;
   - лицензия: MIT/Apache/BSD/MPL; запрещены GPL‑совместимые для серверного кода;
   - не более 20 транзитивных зависимостей на одну библиотеку (иначе нужен отдельный review);
   - репозиторий не в статусе archived/deprecated;
   - присутствуют тесты и базовая документация.

2. В CI обязательно:

   - `govulncheck ./...` на уровне модуля;
   - сканирование Docker‑образов (например, Trivy/Grype).

3. Политика исключений по уязвимостям:

   - допускается временное исключение только при наличии документированного риска и плана обновления;
   - исключения фиксируются в SECURITY.md и в issue‑трекере.

# 3. СТРУКТУРА ПРОЕКТА

Базовая структура для всех Go‑проектов:

```text
/project/
  cmd/                  # точки входа (main)
    api/
    worker/
    cli/
  internal/             # бизнес‑логика (неэкспортируемый код)
    apperrors/          # единые ошибки приложения (sentinel + validation)
    arch/               # architecture tests (опционально)
    communications/     # коммуникации (сообщения/диалоги) — опционально
    config/             # конфигурация и загрузка ENV
    database/           # подключение к БД, миграции, транзакции
    domain/             # доменные сущности, типы, события
    repository/         # доступ к БД/кэшу/очередям
      sqlc/             # сгенерированный из SQL код
    service/            # бизнес‑логика и транзакции
    http/
      handler/          # Echo handlers (тонкий слой)
      dto/              # DTO для HTTP API
      middleware/       # технические middleware
    integrations/       # внешние API, webhooks, очереди
      clients/          # клиенты внешних сервисов
    jobs/               # фоновые задачи/воркеры — опционально
    shared/             # shared tech packages (pagination, query и т.п.)
    components/         # повторно используемые бизнес‑компоненты
  pkg/                  # утилитарные пакеты без бизнес‑логики
  migrations/           # миграции БД
  docs/                 # документация (OpenAPI, ADR и т.п.)
  .golangci.yml
  go.mod
  go.sum
```

Правила:

1. Весь приватный код — в `internal/`. Импорт из `internal` возможен только внутри текущего модуля.
2. `cmd/*` содержит только wiring/инициализацию, но не бизнес‑логику.
3. `pkg/` — только реиспользуемые утилиты без бизнес‑логики и привязки к конкретной БД/ERP.
4. Циклические зависимости между пакетами запрещены. Нарушение считается блокирующей ошибкой CI.
5. Для контроля архитектуры используются architecture‑tests (`internal/arch`) или статический анализ (go vet plugins), валящие сборку при нарушении слоёв.

## 3.1. Правила именования (Go‑код, пакеты, бинарники, скрипты)

1. **Пакеты**

   - Названия пакетов **только в нижнем регистре**, без `CamelCase`, без точек, без дефисов.
   - Допускаются короткие названия с подчёркиваниями только в технических пакетах (`sqlc`, `http`, `pgxutil`), в бизнес‑коде — предпочтительно просто `billing`, `license`, `counterparty`, `document`.
   - Запрещены абстрактные имена `utils`, `helpers`, `common`, если в пакете есть бизнес‑логика.
   - Исключение: технические пакеты допускают слово `helpers`, если в них **нет** бизнес‑логики и они решают инфраструктурную задачу (например, `internal/repository/helpers`, `internal/shared/*`).

2. **Go‑файлы**

   - Имена файлов — `snake_case`.
   - Допустимые суффиксы:
     - `_handler.go` — HTTP/gRPC‑хендлеры;
     - `_service.go` — сервисный слой;
     - `_repository.go` — репозитории;
     - `_dto.go` — DTO для транспорта;
     - `_middleware.go` — middleware;
     - `_integration.go` — внешние интеграции;
     - `_component.go` — бизнес‑компоненты;
     - `_test.go` — тесты.
   - В одном файле — только связанные по смыслу типы/функции.

3. **Типы и интерфейсы**

   - Экспортируемые типы и интерфейсы — `PascalCase`.
   - Не использовать префиксы `I` и суффиксы `Interface` для интерфейсов (`Validator`, а не `IValidator`).
   - Не использовать суффиксы `DTO`, `Model` в именах типов; для этого есть отдельные пакеты `dto`, `domain`.

4. **Функции и методы**

   - Экспортируемые функции/методы — `PascalCase`.
   - Неэкспортируемые — `camelCase`.
   - Названия должны описывать действие: `CreateInvoice`, `UpdateLicenseStatus`, а не `DoWork`, `Handle`.

5. **Переменные и компоненты**

   - Локальные переменные — `camelCase`.
   - Компоненты в коде именуются существительными/ролями: `licenseValidator`, `tariffCalculator`, `invoiceBuilder`.
   - Константы — `UPPER_SNAKE_CASE`.

6. \*\*Бинарники и директории в \*\*``

   - Директории в `cmd/` соответствуют имени бинаря.
   - Имена бинарей и директорий — `kebab-case` или одно слово в нижнем регистре:
     - `cmd/api`, `cmd/worker-billing`, `cmd/iot-agent`.
   - Бинарь должен однозначно отражать роль процесса (не `cmd/app`, а `cmd/erp-api`).

7. **Скрипты (bash/sh, вспомогательные утилиты)**

   - Все скрипты лежат в `scripts/` или `tools/`.
   - Имя файла — `kebab-case` без пробелов:
     - `migrate-up.sh`, `migrate-down.sh`, `generate-openapi.sh`, `dev-up.sh`, `dev-down.sh`.
   - Первый рядок скрипта — shebang `#!/usr/bin/env bash` или `#!/usr/bin/env sh`.

8. **Миграции БД**

   - Формат имени файла миграции совместим с `golang-migrate`:

     ```text
     YYYYMMDDHHMMSS_description.up.sql
     YYYYMMDDHHMMSS_description.down.sql
     ```

   - `description` — `snake_case`, только латинские буквы и цифры, без пробелов и русских символов.

9. **ENV‑переменные**

   - Названия — `UPPER_SNAKE_CASE`.
   - Обязателен префикс сервиса/домена:
     - `ERP_API_DB_DSN`, `ERP_API_JWT_SECRET`, `IOT_AGENT_GRPC_ENDPOINT`.
   - Чувствительные переменные (`*_SECRET`, `*_TOKEN`, `*_PASSWORD`) не логируются и не выводятся в debug.

10. **Kubernetes‑объекты (в части Go‑сервиса)**

    - `Deployment`, `Service`, `ConfigMap`, `Secret` и другие объекты именуются по схеме:
      - `<system>-<service>-<role>` в `kebab-case`, например: `erp-api-backend`, `iot-agent-gateway`.
    - Лейблы и аннотации должны включать минимум: `app`, `component`, `version`.

Нарушение правил именования в новых файлах рассматривается как ошибка ревью и должно исправляться до merge.

# 4. ECHO И РАЗДЕЛЕНИЕ СЛОЁВ

## 4.1. Базовый принцип

- Handler (Echo) = тонкий адаптер между транспортом и сервисом.
- Service = вся бизнес‑логика, транзакции, интеграция доменных операций.
- Repository = SQL/хранилища, без бизнес‑логики.
- Domain = чистые бизнес‑типы без зависимостей от фреймворков.
- Components (camelCase) = повторно используемые бизнес‑алгоритмы.

Echo **не должен** знать про доменную модель и бизнес‑правила.

## 4.2. Запрещено в handler‑слое

1. Бизнес‑логика (любые правила ERP/CRM, биллинг, статусы, тарифы).
2. Любые запросы к БД или кэшам напрямую.
3. Открытие/закрытие транзакций.
4. Передача `echo.Context` в сервисы или репозитории.
5. Запись бизнес‑данных в `echo.Context`.
6. Использование `c.Bind()` для сложных структур без явного DTO и валидации.
7. Формирование произвольных форматов ошибок (только через централизованный ErrorHandler).

## 4.3. Запрещено в service‑слое

1. Любые вызовы Echo API (`c.JSON`, `c.Bind`, `c.Query`, `c.Param` и т.п.).
2. Формирование HTTP‑ответов и статус‑кодов.
3. Использование middleware внутри сервисов.
4. Создание соединений с БД напрямую (только через `database`/`repository`).
5. Логирование без `request_id`/`trace_id`.

## 4.4. Запрещено в repository‑слое

1. Любая бизнес‑логика (валидации, проверки прав, статусы, тарифы).
2. Выполнение более одной бизнес‑операции за вызов.
3. Запросы вне переданного `pgx.Tx` или `pgxpool.Pool`.
4. Использование глобального контекста или `echo.Context`.

## 4.5. Принцип «одна операция — один service‑метод»

1. Один публичный метод сервиса отвечает за **одну** чётко определённую бизнес‑операцию.
2. Нельзя смешивать несколько независимых бизнес‑операций в одном методе.
3. Взаимодействие нескольких сервисов (orchestration) выносится в application‑сервисы или отдельный слой orchestration.

## 4.6. Компоненты (camelCase)

Повторно используемая бизнес‑логика выносится в компоненты:

- `licenseValidator`
- `documentRenderer`
- `tariffCalculator`
- `invoiceBuilder`
- `counterpartyResolver`
- `notificationSender`

Если логика используется более чем в одном сервисе/хендлере — она живёт в компоненте.

## 4.7. Единые ошибки (`internal/apperrors`)

1. Единый источник правды для ошибок приложения — `internal/apperrors` (stdlib‑only, без `pgx`/`echo`).
2. Сервисный слой и домен используют ошибки **только** из `internal/apperrors` (включая `ValidationError`).
3. Дублирование sentinel errors в `internal/service/*` и `internal/repository/*` запрещено (не должно быть отдельных `errors.go` с `ErrNotFound` и т.п.).
4. Handler маппит ошибки в HTTP‑коды через `apperrors.ErrorCode` и возвращает стандартный `ErrorResponse` (см. раздел 9.2).

## 4.8. Нормализация пагинации (`internal/shared/pagination`)

1. Любая пагинация (page/page_size) нормализуется через `pagination.Normalize(...)` с едиными дефолтами и лимитами.
2. Расчёт `offset` и `pages` делается централизованно (`pagination.Params`, `pagination.CalcPages`).

## 4.9. List‑запросы, сортировка и безопасность (`internal/shared/query`)

1. Для List‑методов с динамическими фильтрами используется Query Builder (`internal/shared/query`), чтобы не копировать сборку SQL.
2. Любая сортировка по параметрам запроса должна быть whitelist‑based (никаких прямых подстановок `sortBy`/`sortOrder` в SQL).
3. При невозможности применить сортировку (невалидный параметр) используется default‑сортировка.

# 5. DTO, DOMAIN, SQL — ЖЁСТКОЕ РАЗДЕЛЕНИЕ

## 5.1. DTO (transport layer)

- Расположение: `internal/http/dto` (и аналогично для других транспортов).
- Поля:
  - Go: `PascalCase`;
  - JSON: `snake_case` (через struct tags).
- Валидация: строго через `go-playground/validator` или эквивалент.
- DTO не используется как domain‑модель и наоборот.

## 5.2. Domain

- Расположение: `internal/domain`.
- Структуры **без** JSON‑тегов.
- Содержат только бизнес‑атрибуты и логику.
- Не импортируют Echo, pgx, sqlc и другие инфраструктурные пакеты.

## 5.3. SQL‑модели (sqlc)

- Расположение: `internal/repository/sqlc`.
- Используются только в репозиториях.
- Запрещено прокидывать sqlc‑структуры в сервисы или handler’ы.
- Преобразование: sqlc → domain → DTO выполняется явно.

# 6. БАЗЫ ДАННЫХ

## 6.1. PostgreSQL

### 6.1.1. UUID политика

- Все ключи и внешние ключи — `UUID`.
- UUID генерируется **исключительно** в PostgreSQL (UUID v7).
- Стандартный генератор UUID v7: ✅ `pg_catalog.uuidv7()` (PostgreSQL 18+).
- Go генерирует UUID только для SQLite и локальных утилит.

**Практика:**
- Всегда используйте schema-qualified вызов `pg_catalog.uuidv7()` (не зависит от `search_path`).
- Для PK/FK default: `DEFAULT pg_catalog.uuidv7()`.
- Быстрая проверка в БД:

```sql
SELECT pg_catalog.uuidv7();
SELECT pg_catalog.uuid_extract_version(pg_catalog.uuidv7());   -- 7
SELECT pg_catalog.uuid_extract_timestamp(pg_catalog.uuidv7()); -- timestamptz

CREATE TEMP TABLE tmp_uuidv7_test (id uuid PRIMARY KEY DEFAULT pg_catalog.uuidv7());
INSERT INTO tmp_uuidv7_test DEFAULT VALUES RETURNING id;
```

### 6.1.2. Схемы

Текущий минимальный набор схем (MVP):

- `erp` — все бизнес‑таблицы приложения (CRM/ERP/интеграции)
- `public` — только расширения (uuid-ossp/pgcrypto) и исторические таблицы, которые уже в `public`

Дополнительные схемы (`system/core/crm/integrations`) вводятся только при наличии DBA‑поддержки и прав `CREATE SCHEMA` у роли миграций.
- `portal` — публичные кабинеты
- `metrics` — бизнес‑метрики
- `logs` — технические логи, аудит

### 6.1.3. Автонумерация (без гонок)

1. Автонумерация выполняется только внутри транзакции через `SELECT ... FOR UPDATE`.
2. Шаблон:

```sql
BEGIN;
SELECT last_number
  FROM system.numbers
 WHERE series_id = $1
 FOR UPDATE;

UPDATE system.numbers
   SET last_number = last_number + 1
 WHERE series_id = $1;

COMMIT;
```

3. Формат номера: `${PREFIX}-${NUMBER}` или иной зафиксированный формат.

### 6.1.4. Enum registry

Вместо жёстких ENUM‑типов используется таблица‑реестр:

```text
id, domain, code, label, color, is_system
```

- Любые статусы и перечисления хранятся в едином реестре.
- ALTER TABLE для добавления статусов запрещены; изменения только через данные.

### 6.1.5. Soft delete

- Для всех бизнес‑сущностей используется `is_deleted BOOLEAN NOT NULL DEFAULT false`.
- Физический DELETE разрешён только для временных/технических таблиц.

### 6.1.6. Транзакционная согласованность

- Любая сложная бизнес‑операция выполняется в рамках транзакции `SERIALIZABLE` или `REPEATABLE READ` (по согласованию для сервиса).
- Частично выполненные операции запрещены, всегда либо `COMMIT`, либо `ROLLBACK`.
- В транзакции не должно быть внешних сетевых вызовов (HTTP, gRPC), только работа с БД и внутренним состоянием.

## 6.2. SQLite

SQLite используется только для:

- embedded‑микросервисов (локальные агенты, IoT‑шлюзы);
- desktop/edge‑бинарей;
- интеграционных/юнит‑тестов.

Обязательные настройки:

- WAL‑режим;
- `busy_timeout = 5000ms`;
- `foreign_keys = ON`;
- кэш ≥ 64MB;
- разделение reader/writer‑подключений.

UUID:

- генерируется в Go (`uuid.New()`), формат и стратегия соответствуют основной системе.

# 7. ТРАНЗАКЦИИ

## 7.1. Где создаются транзакции

- Только service‑слой может начинать транзакцию.
- Repository никогда не создаёт и не завершает транзакции, а только использует переданный `pgx.Tx`.

## 7.2. Шаблон транзакции

```go
func (s *Service) DoSomething(ctx context.Context, req dto.Request) (dto.Response, error) {
    tx, err := s.db.BeginTx(ctx, pgx.TxOptions{})
    if err != nil {
        return dto.Response{}, fmt.Errorf("begin tx: %w", err)
    }

    var resp dto.Response

    defer func() {
        if err != nil {
            _ = tx.Rollback(ctx)
        }
    }()

    if err = s.repo.Action1(ctx, tx, req); err != nil {
        return resp, err
    }

    if err = s.repo.Action2(ctx, tx, req); err != nil {
        return resp, err
    }

    if err = tx.Commit(ctx); err != nil {
        return resp, fmt.Errorf("commit tx: %w", err)
    }

    return resp, nil
}
```

Все операции, требующие целостности (нумерация, статусы, документные действия, биллинг), выполняются только внутри транзакции.

# 8. БИЗНЕС‑ЛОГИКА

## 8.1. Общие правила

1. Каждая бизнес‑операция оформляется отдельным методом сервиса.
2. Вся логика статусов, проверок прав, расчётов тарифов, биллинга, лицензий реализуется только в сервисах и компонентах.
3. Все сущности используют soft delete (`is_deleted`).
4. Domain‑модели независимы от транспорта и БД.

## 8.2. Idempotency

1. Для create‑операций, которые могут быть вызваны повторно, обязателен `Idempotency-Key` в заголовке.
2. В БД должна быть уникальная гарантия (UNIQUE + транзакция) по ключевым полям.
3. Все webhook‑handler’ы обязаны быть идемпотентны и хранить `event_id` и статус обработки.

# 9. HTTP API И OPENAPI

## 9.1. OpenAPI как единственный источник правды

1. `openapi.yaml` (или `openapi/*.yaml`) — первичный источник описания API.
2. Swagger‑комментарии в коде запрещены.
3. Любое изменение API начинается с изменения OpenAPI‑схемы.

## 9.2. Правила для схем

1. Все модели описываются в `components/schemas`.
2. Inline‑описания объектов запрещены.
3. Обязательные поля для бизнес‑сущностей: `id`, `createdAt`, `updatedAt`.
4. Глубина вложенности объектов — не более 2 уровней (для больших структур — отдельные схемы).
5. Формат ошибки стандартизирован:

```json
{
  "error": "string",
  "code": "string",
  "details": {"...": "..."}
}
```

6. `code` — обязательный машиночитаемый код из `components/schemas/ErrorCode` (см. OpenAPI).
7. `error` — человекочитаемое сообщение (не использовать как код ошибки).
8. Для ошибок валидации обязательно заполняется `details.field`.

## 9.3. Генерация кода

1. `oapi-codegen` запускается после каждого изменения схемы.
2. В PR не допускается diff между `openapi.yaml` и сгенерированными файлами.
3. Генерация покрывает:
   - server interface;
   - DTO/models;
   - валидацию входящих данных.

# 10. АУТЕНТИФИКАЦИЯ И АВТОРИЗАЦИЯ

## 10.1. JWT Policy

1. Для внутренних монолитных/одно‑сервисных сценариев допускается HS256:

   - обязательный `kid` в header;
   - ротация ключей не реже 1 раза в 90 дней;
   - хранение ключей только в Vault/Kubernetes Secrets.

2. Для межсервисного и внешнего взаимодействия обязательны асимметричные алгоритмы:

   - RS256/ES256;
   - централизованный IdP (Keycloak/другой), либо выделенный auth‑сервис.

## 10.2. Claims

Обязательные claims:

- `sub` — идентификатор пользователя/субъекта;
- `exp` — срок действия (≤ 24h);
- `iat` — время выпуска токена;
- `iss` — issuer (проверяется);
- `aud` — audience (проверяется).

Дополнительные claims:

- `scope`/`role` — роли и права, значения берутся из централизованного реестра;
- любые бизнес‑атрибуты, не содержащие чувствительных данных.

## 10.3. Middleware

1. Middleware обязано извлекать `user_id`, `trace_id`, `request_id` и пробрасывать их в контекст.
2. В middleware запрещено выполнять доменную логику (только техоперации: аутентификация, rate limiting, логирование, CORS).

# 11. ИНТЕГРАЦИИ И ВНЕШНИЕ СЕРВИСЫ

## 11.1. Retry/Backoff

1. Для всех внешних запросов (HTTP, gRPC, очереди) используется экспоненциальный backoff.
2. По умолчанию: max 5 попыток, jitter.
3. Повторяемые операции обязаны быть идемпотентны.

## 11.2. Circuit breaker

1. Используется `sony/gobreaker` (или аналог) для всех критичных интеграций.
2. Состояние breaker логируется и мониторится.

## 11.3. Observability интеграций

1. Каждый запрос во внешний сервис создаёт отдельный span.
2. В логах обязательно указываются:
   - endpoint,
   - статус,
   - latency,
   - correlation IDs.

## 11.4. Размещение логики

- Вся логика обращения к внешним сервисам живёт в `internal/integrations/clients/`.
- Handler’ы/сервисы не обращаются к внешним API напрямую, только через интеграционные компоненты.

## 11.5. Размещение инетграций

мы стараемся минимизировать количество секретов в .env и всю интеграцию вынести в подключаемые модулю (s3, почта resend, openAi и тд), чтобы пользователи могли уже в интерфейсе управлять включение, расширением и внесением секретов. Секреты записываются непосредственно в БД в таблица credentials с шифрованием pgcrypto по токену из .env.

# 12. ЛОКАЛЬНЫЕ ПРИЛОЖЕНИЯ И EDGE‑СЦЕНАРИИ

1. База данных — SQLite embedded.

3. Middleware‑цепочка упрощается, но:
   - обязательно panic‑recovery;
   - обязательное базовое логирование и трассировка (даже если офлайн).
4. Сборка — кроссплатформенная через `GOOS/GOARCH`.

# 13. ЛОГИРОВАНИЕ И НАБЛЮДАЕМОСТЬ

## 13.1. Unified logs

Каждая запись лога обязана содержать:

- `timestamp`
- `level`
- `service`
- `version`
- `request_id`
- `trace_id`
- `user_id` (если есть)
- `method`, `path`, `status`
- `duration_ms` для запросов

## 13.2. Правила логирования

1. Запрещено логировать:
   - пароли;
   - токены доступа;
   - секреты интеграций;
   - полные персональные данные (ПДн) без обоснования.
2. Большие payload’ы и ответы режутся до разумного размера (truncation).
3. Для повторяющихся ошибок используется rate limiting логов.

## 13.3. OpenTelemetry

1. Обязателен OTel‑middleware для:
   - HTTP (Echo);
   - pgx;
   - Redis;
   - runtime (GC, heap, goroutines).
2. Для legacy‑сервисов допускается авто‑инструментирование, но с контролем накладных расходов.
3. Для бизнес‑критичных операций (биллинг, лицензии, интеграции) обязательно наличие доменных спанов.

# 14. ТЕСТИРОВАНИЕ

## 14.1. Unit‑тесты

1. Минимальное покрытие на уровне модуля: **≥ 40%**.
2. Для доменных и сервис‑слоёв целевое покрытие: **≥ 70%**.
3. Запуск:

```bash
go test -v -race -coverprofile=coverage.out ./...
```

4. Все тесты обязаны быть зелёными, гонки запрещены.

## 14.2. Integration tests

1. Используется SQLite in‑memory либо тестовый контур PostgreSQL.
2. Интеграционные тесты покрывают:
   - основные бизнес‑флоу;
   - транзакции;
   - интеграции с внешними сервисами (через моки/тестовые стенды).

## 14.3. OpenAPI tests

1. Схема проходит линтинг (Redocly или аналог).
2. Генерация кода из схемы не даёт diff’ов в PR.

## 14.4. Fuzz‑тесты

1. Для всех парсеров внешних payload’ов (webhooks, импорт/экспорт, формулы) обязательны fuzz‑тесты.
2. Запуск через нативный `go test -fuzz=...`.

## 14.5. Нагрузочные тесты

1. Для каждого публичного API‑сервиса должны быть сценарии нагрузочного тестирования (k6/JMeter/Vegeta).
2. Результаты (RPS, p95/p99 latency, error rate) документируются и привязываются к версиям сервиса.

# 15. КОНФИГУРАЦИЯ И СЕКРЕТЫ

## 15.1. Конфигурация

1. Вся конфигурация — через ENV‑переменные.
2. Используется `caarlos0/env` (или аналог) для маппинга ENV → struct.
3. Значения по умолчанию допускаются только для не‑секретных параметров.

## 15.2. Redis

1. В production используется только `rediss://`.
2. Обязательно включена проверка TLS‑сертификатов.

## 15.3. Secrets

1. В Go‑коде секреты не хардкодятся и не лежат в `.env` в репозитории.
2. Хранение секретов:
   - локально — только в переменных окружения во время разработки;
   - CI/CD — только в Secret‑хранилищах (GitHub Secrets, аналогичные механизмы);
   - k8s — `Secrets` или внешние Vault‑решения.
   - подключаемые модули внешних интеграций с хранением в БД
3. Чувствительные данные в БД хранятся в зашифрованном виде (pgcrypto/внешние KMS‑решения).
4. Ротация секретов проводится по регламенту безопасности и фиксируется.

## 16.1. GitHub Actions — минимальные обязательные правила

```bash
golangci-lint run ./...

```

Требования:

```bash

```

Требования:

- успешная сборка всех целевых бинарей;

```bash
npx @redocly/cli lint openapi.yaml
```

```bash
oapi-codegen --config oapi-config.yaml openapi.yaml
```

```bash
govulncheck ./...
```

- High/Critical CVE запрещены без оформленного исключения.

- multi‑stage Dockerfile;
- успешная сборка;
- итоговый образ ≤ 60MB (для API/worker‑сервисов).

1. Все CI‑jobs зелёные.

3. Соблюдён semver:
   - MAJOR — breaking changes;

4. Обновлён OpenAPI, если API изменён.
5. Выполнена генерация oapi‑codegen; в PR нет diff’ов между схемой и кодом.
6. Добавлены миграции при изменении БД и обновлена MIGRATIONS.md.
7. Добавлены тесты на новую логику.
8. Нет TODO/закомментированного кода.
9. Логи включают `request_id`/`trace_id`.
10. `govulncheck` и сканер образов не нашли критичные уязвимости или есть задокументированные исключения.

# 17. KUBERNETES И ДЕПЛОЙ В КЛАСТЕРЫ

## 17.1. Общие требования

1. Все API‑сервисы разворачиваются в Kubernetes (k3s/managed‑k8s).
2. Stateless API — единственный допустимый тип сервисов в этом стандарте (stateful только для согласованных компонентов).
3. Обязательны readiness/liveness/startup probes.

## 17.2. Ресурсы и масштабирование

1. Для каждого Pod обязательно заданы:
   - `resources.requests`;
   - `resources.limits`.
2. Настроен `HorizontalPodAutoscaler` минимум по CPU, рекомендуется также по RPS/latency.
3. Для критичных сервисов настраиваются `PodDisruptionBudget`.

## 17.3. Безопасность в Kubernetes

1. Используются PodSecurity/аналогичные механизмы:
   - `runAsNonRoot`;
   - `readOnlyRootFilesystem`;
   - минимальный набор Linux‑capabilities.
2. NetworkPolicies ограничивают трафик между сервисами до необходимого минимума.
3. Доступ к БД/кэшу/очередям ограничен только нужными namespace/подами.

## 17.4. Образы и политика pull

1. Используются **immutable‑теги** образов (semver или commit‑hash).
2. `imagePullPolicy: IfNotPresent` для версионированных тегов.
3. Обновление производится только через выпуск нового тега, не через перезапись старого.

## 17.5. Стратегии релизов

1. Минимум — rolling update с корректно настроенными probes.
2. Для критичных сервисов — blue‑green/canary‑релизы.
3. Обязателен быстрый rollback (через сохранённые предыдущие deployment‑манифесты).

## 17.6. Логи и трейсинг

1. Логи в формате JSON отправляются в централизованное хранилище.
2. OTel‑экспорт настроен на общий observability‑стек.
